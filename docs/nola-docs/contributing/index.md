# 参与贡献

Nola Translator 接受文档、代码、复现材料、模型验证和界面反馈等贡献。可以从一个错误段落或可复现缺陷开始，不需要先完成整个功能才能参与。

本节说明贡献入口和写作要求，开发工具链见[开发者指南](../developers/index)。

## 一、可以贡献什么

| 方向 | 有帮助的产出 | 需要的依据 |
| --- | --- | --- |
| 文档 | 补全步骤、更新截图、修正链接 | 实际界面与可执行验证 |
| 缺陷 | 最小复现、测试或修复 | 预期、实际及失败阶段 |
| 模型 | 兼容性验证或预设建议 | 官方模型卡、许可证和语言能力 |
| 界面 | 可重现的交互与布局改进 | 任务、窗口尺寸及截图 |
| 工程 | 协议、组件、安装或性能改进 | 边界、测试和兼容范围 |

搜索已有 Issue 与 PR 后再确定范围，避免重复实现或让相邻页面产生冲突。

## 二、先阅读哪些页面

- [如何贡献](./how-to-contribute)：从 Fork、分支到预览、检查、提交和审核的完整流程。
- [编写规范](./writing-guidelines)：依据 PCLC 原文逐类改编的收录、写作、排版和维护规则。
- [开发环境配置](../developers/development-setup)：前端、Python、文档、扩展和打包环境。
- [如何反馈](../troubleshooting/feedback)：只报告问题时的材料和隐私要求。

## 三、贡献的基本边界

只提交有权贡献的内容。第三方代码、模型、文档与图片需要核实许可，署名和改编要求不能因复制到本仓库而消失。

文档必须核对真实功能，不能把其他软件的操作、硬件要求或账号协议替换名称后直接套用。模型能力和费用等结论要有来源，没有实测时明确范围。

代码修改遵守 `AGENTS.md` 与 `DESIGN.MD`。协议需要同步多端类型和校验，界面文案需要完整区域词典，结构变化需同步维护规范。

## 四、提交与审核

每个分支围绕明确目标，提交前检查差异、隐私和相应构建。PR 说明问题、最终行为、验证及未验证内容；UI 改动附图，数据行为改动说明影响。

维护者可能要求调整范围或补充证据。回应审核时继续更新原分支，方案变化同步更新正文和 PR 描述，不保留失效结论。

项目使用英文提交信息；AI 助手执行提交前要先展示并取得用户确认。完整格式和示例见[如何贡献](./how-to-contribute)。
